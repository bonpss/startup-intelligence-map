# Story 2.1: Build `diagnose_scraping.py`

Status: done

## Story

As a Julien,
I want a read-only script that samples scraped sites and characterizes the failure types it finds,
so that I have persisted evidence of scraping heterogeneity before deciding whether/how to fix extraction.

## Acceptance Criteria

1. **Given** URLs for sites already present in `compspro`, **when** `diagnose_scraping.py` runs, **then** it keeps sampling until no new failure type has appeared across N consecutive *newly-characterized* sites (N a revisable module-level constant, e.g. `STABILITY_WINDOW = 5` — same "stability window" pattern as Story 4.1's own signal, but a separate constant; do not hardcode a bare literal, and avoid a degenerately small value like 1, which would stop after the very first site), rather than a fixed sample size decided blind.
2. **And** it re-runs `scrape()` (`main.py`) on each sampled site and characterizes the result (incomplete content, blocking page, content drowned in noise, etc. — the failure-type vocabulary itself stays intentionally open, free text; only the script's stopping condition is being pinned down here).
3. **And** each characterization is written directly to `quality_review_log` via `storage.save_quality_review()` (`review_type='scraping_diagnostic'`, `subject`=site domain — normalization already enforced internally by `save_quality_review()`, built in Story 1.2), not to a local ephemeral report.
4. **And** before re-characterizing a domain, the script queries `quality_review_log` (using the same normalized form) to avoid duplicating an already-known diagnosis (AD-7 — no separate local state file); two URL variants of the same site (e.g. `https://Example.com/` and `example.com`) must resolve to one `subject`, not two.
5. **And** the script never writes anywhere other than `quality_review_log` — no modification to `compspro` or `competitors` (AD-5, diagnosis-only).

## Tasks / Subtasks

- [x] Task 1: Sample candidate sites, deduped against already-diagnosed domains (AC: #1, #4)
  - [x] Fetch all non-null `website` values from `compspro` via `_client()` imported from `storage.py` — do **not** add a new `storage.py` wrapper function for this; the existing project convention for ad hoc `compspro` reads is the calling script querying `_client().table("compspro").select(...)` directly (see `reprocess_list.py:33-43`, `main.py:260`, `competitor_validator.py`) — `storage.py` only needs to be the sole place the Supabase *client* is instantiated (AD-1), not the sole place every query is written.
  - [x] Randomize the order (`random.shuffle`) before sampling so "different site types" isn't biased by insertion/creation order.
  - [x] Before scraping a candidate, call `storage.get_quality_reviews('scraping_diagnostic', subject=website)` — pass the raw `website` value, do not pre-normalize (see Dev Notes). If it returns any rows, skip this candidate (already diagnosed) and move to the next; skipped sites do **not** count toward the "N consecutive" stopping condition in Task 3 (they produced no new characterization).
- [x] Task 2: Scrape and characterize each not-yet-diagnosed sampled site (AC: #2)
  - [x] Import `scrape` from `main.py` and call it as `asyncio.run(scrape(url))` from this (synchronous, top-level) script — exact pattern already used by `reprocess_list.py:47`. Ignore the second tuple element (`logo_candidates`) — irrelevant to diagnosis.
  - [x] Wrap the call in `try/except Exception` (matches this codebase's existing broad-except convention — see Consistency Conventions) — a raised exception (navigation timeout, DNS failure, etc.) is itself diagnostic signal, not a reason to crash and lose the run's progress. Record it as its own failure-type verdict (e.g. `scrape_exception`) rather than skipping the site silently.
  - [x] Apply a heuristic characterization function to the returned markdown (or the caught exception) that returns a short, non-empty, reusable label. `verdict` for `review_type='scraping_diagnostic'` has **no app- or DB-level vocabulary constraint** (AD-4) — unlike `taxonomy_split`'s closed 4-value set — so this is a genuine design choice, not a fixed contract. A reasonable starting set (rename/extend freely, but reuse the *same* label for the *same* kind of failure across sites in a run — AC #1's stopping condition depends on label consistency, not prose creativity): `ok` (nothing wrong), `incomplete_content` (markdown far shorter than a normal page), `blocking_page` (markdown shows cookie-wall/CAPTCHA/"enable JavaScript"-style blocking text instead of real content), `content_drowned_in_noise` (nav/footer/boilerplate dominates over actual product content), `scrape_exception` (the `try` above raised).
  - [x] Do not modify or duplicate `scrape()`'s own resilience logic (SSL fallback, cookie-banner removal, wait-for-content heuristics in `main.py:155-207`) — this script's job is to *observe* what `scrape()` returns today, not to make scraping better.
- [x] Task 3: Persist each characterization and track the stopping condition (AC: #1, #3)
  - [x] Call `storage.save_quality_review(review_type='scraping_diagnostic', subject=url, verdict=<label>, notes=<short detail, e.g. markdown length or the matched trigger phrase>)` — pass the raw `website`/`url` as `subject`; `save_quality_review()` normalizes it internally (Story 1.2), do not call `normalize_domain()` yourself first.
  - [x] Maintain, for the current run, a running set of verdict labels seen so far and a "consecutive-no-new-label" counter: increment on a repeat label, reset to 0 on a genuinely new label, stop sampling once the counter reaches the module-level stability constant (Task 1's random order + this loop together implement AC #1).
  - [x] Handle exhaustion explicitly: if the shuffled candidate list runs out (every candidate was either characterized or already-known) before the stability counter is reached, stop gracefully and report that the sample was exhausted rather than looping or crashing — this is a valid, non-error stopping outcome, not just the stability condition.
- [x] Task 4: CLI entry point and run summary (no dedicated AC — matches every other entry-point script in this project being runnable standalone, e.g. `main.py`'s `if __name__ == "__main__":` block)
  - [x] No command-line arguments needed — AC #1's "Given" is "URLs for sites already present in compspro" as a whole, not scoped to one subsector or domain.
  - [x] Print a line per site as it's processed (domain + verdict) and a final summary on exit: count newly characterized, count skipped as already-known, and which of the two stop reasons ended the run (stability reached vs. sample exhausted).

## Dev Notes

- **AD-1 (single Supabase access point):** `storage.py` is the only place `create_client()`/`supabase-py` is called directly. This script imports `_client` from `storage.py` for its own `compspro` sampling query (Task 1) — exactly like `main.py`, `reprocess_list.py`, and `competitor_validator.py` already do — and imports `save_quality_review`/`get_quality_reviews` for all `quality_review_log` access. Never call `.table("quality_review_log")` directly from this script; always go through those two functions.
- **AD-5 (asymmetric diagnosis paths):** `diagnose_scraping.py` writes its own `scraping_diagnostic` findings directly as it runs — this is automated characterization data, not a deliberated human verdict, so (unlike `log_review.py`'s future `taxonomy_split` writes) there is no reading-rubric gate to build here. Do not add one. Also: do not touch `graph_analysis.py` — it stays strictly read-only per AD-5 and is unrelated to this story, but it's an adjacent file in the same architecture area, easy to accidentally reach for.
- **`storage.normalize_domain()` (Story 1.2, already built and exported) does not need to be called directly here.** Both `save_quality_review()` (`storage.py:69`) and `get_quality_reviews()` (`storage.py:115`) already normalize the `subject` internally for `review_type='scraping_diagnostic'` — pass the raw `website`/URL value straight through to both. Calling `normalize_domain()` yourself first would be redundant, not wrong, but adds nothing.
- **`main.scrape(url)` signature:** `async def scrape(url: str) -> tuple[str, list[dict]]`, returns `(markdown, logo_candidates)` (`main.py:155`). Call it with `asyncio.run(scrape(url))` from this synchronous script — do not make the whole script `async`; `reprocess_list.py:47` is the exact existing precedent for this call shape.
- **Verdict vocabulary is deliberately open** (AD-4) — resist the urge to over-engineer a taxonomy of failure types up front. The one hard requirement is *consistency within a run*: reusing `"blocking_page"` for every blocking page you see, not inventing a new string each time, since AC #1's stability window only works if repeats are recognized as repeats.
- No new dependency and no `requirements.txt` change — `random`/`asyncio` are stdlib; `scrape`, `_client`, `save_quality_review`, `get_quality_reviews` are all already-existing imports from `main.py`/`storage.py`.
- No test suite for this story. Story 1.2's unit test was an explicitly scoped, one-off exception to this project's no-test convention (justified there because `save_quality_review()` is the single access point every other story writes through) — that exception does not carry forward to Epic 2.
- No migration — no schema change in this story.
