### Review Findings

- [x] [Review][Decision] Unique constraint on `(review_type, subject)`? — **Resolved by Julien: no constraint, history is intentional.** Consistent with FR-5's own founding reason for being a table rather than another overwritten report — re-diagnosing a subsector or re-characterizing a domain should produce a comparable new row, not silently overwrite the prior trace. No code change.
- [x] [Review][Decision] Add an `updated_at` column? — **Resolved by Julien: yes, add it.** `resolution` is populated after initial write; without `updated_at` the gap between "diagnosed" and "resolved" is unrecoverable, which matters directly for a table whose purpose is being a decision/audit record. → converted to a patch item below.
- [x] [Review][Patch] `id` column: use `generated always as identity` instead of `generated by default as identity` [migrations/002_harden_quality_review_log_schema.sql] — applied via `alter table ... alter column id set generated always`; verified live (`identity_generation = 'ALWAYS'`)
- [x] [Review][Patch] Block empty-string values on `review_type`/`subject` (NOT NULL doesn't stop `''`) [migrations/002_harden_quality_review_log_schema.sql] — `CHECK` constraints added and verified live
- [x] [Review][Patch] Guard `source_snapshot`'s shape (`jsonb_typeof(source_snapshot) = 'object'` when not null) [migrations/002_harden_quality_review_log_schema.sql] — `CHECK` constraint added and verified live
- [x] [Review][Patch] Add `comment on table`/column comments to the SQL file itself, documenting the RLS-enabled-zero-policies decision inline [migrations/002_harden_quality_review_log_schema.sql] — applied
- [x] [Review][Patch] Add `updated_at timestamptz` column (from resolved decision above) [migrations/002_harden_quality_review_log_schema.sql] — nullable, app-managed (no trigger), consistent with AD-1/AD-2's single-access-point convention; Story 1.2 must set it explicitly on `resolution`/`verdict` updates
- [x] [Review][Defer] Index on `(review_type, subject)` [migrations/001_create_quality_review_log.sql] — deferred, pre-existing scale doesn't warrant it yet (low hundreds of rows expected); revisit if the table grows large enough for sequential scans on FR-3's lookup query to matter.



### Schema DDL (write exactly this into `migrations/001_create_quality_review_log.sql`)

> **Amended by code review:** `migrations/002_harden_quality_review_log_schema.sql` (applied 2026-08-10) adds `generated always` identity, blank-string/shape `CHECK` constraints, table/column comments, and an `updated_at` column on top of this base DDL — see Review Findings below and that file for the current full schema.

```sql
create table quality_review_log (
  id bigint generated by default as identity primary key,
  review_type text not null,
  subject text not null,
  date_diagnosed timestamptz not null default now(),
  source_snapshot jsonb,
  verdict text not null,
  resolution text,
  notes text
);

alter table quality_review_log enable row level security;
```

Column notes (from PRD §4.6 and Architecture AD-2/AD-4/AD-7 — this story only creates columns, it does not enforce the contract below; that's Story 1.2's job in application code):
- `review_type`, `subject`: no DB-level format constraint (AD-7) — validated in `storage.save_quality_review()`, not here.
- `verdict`: **plain `text`, deliberately no DB enum/CHECK** (AD-4) — `taxonomy_split` uses a closed 4-value set (isolated mis-tag / structural gap / scraping artifact / ambiguous) but `scraping_diagnostic`'s failure-type vocabulary is still open/evolving; a DB constraint would break the latter. Do not add a CHECK constraint on this column even though it's tempting.
- `source_snapshot`: `jsonb`, nullable — captures a copy of the relevant slice of `graph_analysis_report.json`'s `subsector_splits` (for `taxonomy_split`) before that file is overwritten by the next run. Not always applicable (e.g. may be null for `scraping_diagnostic` rows), hence nullable.
- `resolution`: nullable — populated when a chantier's fix is known (e.g. "cleanup rule added", "new subsector created"); FR-1's diagnostic rows won't have one yet.
- No foreign keys to `compspro`/`competitors` — `subject` is a denormalized string (subsector name or domain), not a row reference; this matches how the rest of the schema already denormalizes (`competitors.company_a`/`company_b` are names, not FKs to `compspro.id` either — verified by reading `storage.py`).

### RLS — enable, add **zero** policies (important, verified live, don't second-guess this)

This project's runtime Supabase key (`.env`'s `SUPABASE_KEY`, consumed by `storage.py`'s `_client()`) was decoded and confirmed to carry `role: service_role` — **it bypasses RLS entirely**, regardless of policies. Confirmed live via `pg_policies` query (2026-08-10): the existing `compspro`/`competitors` tables also have RLS enabled with no policies targeting them (the `pg_policies` rows that do exist — `startups`, `jobs`, `sources`, `tags`, `job_tags`, `scrape_logs` — belong to an unrelated project sharing this Supabase org; do not touch or reference those tables). Enabling RLS with no policy on `quality_review_log` reproduces the exact same (safe, working) pattern already used for this project's own tables. **Do not add a policy "to be safe" — it isn't needed and isn't the established pattern here.**
